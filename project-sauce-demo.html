QA Case Study:
SauceDemo

Context: SauceDemo is a demo e-commerce site from Sauce Labs, made for people to practice software testing. It works like a small online store: you log in, browse products, sort them, add items to a cart, and go through checkout. It also includes several built-in test accounts that behave differently. One is locked out, one has visual glitches, and one runs slowly. That makes it a realistic place to practice finding and documenting problems.

Problem: In any online store, the path from browsing to buying has to work every time. A broken button, a wrong price, or a cart that loses items costs the business sales and makes customers lose trust. Quality assurance (QA) testing exists to catch those problems before real users do. Your goal was to test the site the way a QA tester would, find where it breaks, and write it up clearly enough that a developer could fix it.

Process: You can explain each stage of how testing works:

  • Planning: Decide what to test and why. The most important user paths, like login and checkout, usually come first.
  • Writing test cases: For each one, list the steps, the expected result, and the actual result. For example: "Add an item to the cart, open the cart, and the item should appear with the correct price."
  • Types of testing: Name the ones you used. Functional testing checks that features do what they should. UI testing checks layout and visuals. Negative testing tries things users shouldn't do, like logging in with a wrong password or checking out with empty fields. Cross-user testing compares how the different test accounts behave.
  • Logging bugs: Explain what makes a good bug report: a clear title, steps to reproduce, expected vs. actual behavior, a severity level (how badly it affects users), and a screenshot.
  • Tools: Mention whatever you used to organize your tests, such as a spreadsheet, Jira, or AI tools for drafting cases or checking coverage.

Solution: Summarize what you found, with numbers if you have them (how many test cases you wrote and how many bugs you found). Highlight your most interesting bug and explain why it mattered for users. End with what you learned about testing and what you would test next, such as mobile screen sizes or accessibility.
